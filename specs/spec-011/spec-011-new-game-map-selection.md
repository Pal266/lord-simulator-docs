# Title

New Game Map Selection and Terrain Loading

# Type

feature

# Description

Enable the existing New Game button to open a terrain-based overview of the generated 100 × 100 km southern_coast_range region. The player selects one of one hundred 10 × 10 km plots and enters its real Unreal Landscape with generated rivers and lakes and a free-flying camera. This is an end-to-end verification of the offline terrain-generation, import, packaging, selection and loading pipeline; it does not introduce gameplay or world simulation. The 100 plots are geographic/rendering partitions of one 100 × 100 km world, not 100 independent simulation worlds. The 100-cell grid does not imply that every plot will ultimately be playable: future specifications will determine eligibility based on economic resources and benefits. This specification tests technical loading for every plot without assigning gameplay eligibility.

# Requirements

1. **Source and reproducibility.** Use the authoritative region definition and offline generation workflow in the documentation repository at `fictional_map/regions/southern_coast_range/region.json` and `fictional_map/regions/southern_coast_range/USAGE.md`, with world seed `7` and the revised canonical region configuration to be supplied by the user for 10 × 10 km tiling. The underlying 100 × 100 km terrain and hydrology remain the same; only the tile export partition and resampling change. The updated source data and exporters are a prerequisite for implementation, not a task for the game implementation agent to invent. Execute the planet and regional generation stages in the order specified by `USAGE.md` and require their applicable validators to pass before import; do not accept a failed or skipped validator as a successful pipeline test. Preserve and record the generation configuration and output identifiers used for the overview, heightmaps and water so all three originate from the same generation run. Do not start implementation until the user-provided updated `region.json`, heightmap exporter, water exporter, corresponding validation tools and generated outputs are available and pass validation; do not modify the scientific terrain or hydrology generation to compensate for missing new tiling data. The source region is 100 × 100 km, divided into a 10 × 10 grid of 10 × 10 km plots, named `tile_x{col}_y{row}` with columns west-to-east (0–9) and rows north-to-south (0–9). Do not synthesize a replacement landscape, use arbitrary test terrain, or regenerate the scientific world in the running game. Document the exact reproducible offline commands, required source files, resulting cooked game assets, and any conversion/import commands in the game project's root README. Large generated exports may be produced locally and need not be checked into the documentation repository.

2. **Import all one hundred real landscapes.** Generate or obtain the outputs from the documented pipeline, run its available scientific/plot validators, and import each of the one hundred actual `export/tile_x{col}_y{row}/heightmap.png` files into Unreal as a separately loadable landscape level. Each input is 16-bit grayscale, 4033 × 4033 vertices, with height encoding `32768 + elevation_metres × 12.8`. Use Unreal X/Y scale `1000000 / 4032` cm (approximately 248.015873 cm) and Z scale 1000, following the documented region workflow. Preserve each plot's correct orientation and elevation; do not independently rescale heights to fit the plot. Each selected level may use its own local origin `(0, 0, 0)` for this rendering test, but preserve a deterministic mapping from each tile's local coordinates to its position in the shared 100 × 100 km world. Level identity and actor lifetime must not be treated as the identity or lifetime of a future world simulation. Preserve the north-up tile convention, with `tile_x0_y0` at the northwest corner and `tile_x9_y9` at the southeast corner. The level must be cooked and loadable in a packaged Windows build without requiring Python, the documentation repository, or external heightmap files at runtime.

3. **Minimal terrain presentation.** Show the actual landscape geometry with one newly created, non-textured, opaque Unreal material using a constant Base Color RGB `(0.45, 0.45, 0.45)`, Metallic `0`, and Roughness `1`; no imported artistic texture, biome shading, foliage, roads, structures, NPCs, lighting effects selected for art direction, or other world content is required. Use one directional light (white, intensity `3` lux, rotation pitch `-45°`, yaw `-45°`) and one skylight with intensity scale `1`, with no artistic post-processing. Rivers and lakes are required as defined below. Do not introduce new third-party dependencies or approved visual assets.

4. **Generated rivers and lakes.** Run the documented `export_water.py` and `validate_water.py` stages after terrain generation. For every selectable plot, use its actual `export/tile_x{col}_y{row}/water.json` output to place rivers and lakes in the corresponding Unreal level. Use Unreal Engine's built-in Water plugin and the repository's `scripts/ue_import_water.py` editor import workflow as the starting point. The import must run during content preparation in the Unreal Editor, not in the packaged game. Preserve the exported river spline locations, water elevations and widths, and the exported lake outlines and water elevations; Treat exported river depth and velocity as nonessential metadata for this visual pipeline test: do not require them in Unreal and do not invent substitute values. River location, width and water-surface elevation, and lake boundary and water-surface elevation, are mandatory. The water surfaces must align with the actual terrain channels and lake basins. Water must not deform the landscape: the heightmaps already contain the channels and basins. Basic engine water appearance is sufficient; no custom water artwork, hydrodynamic simulation, flooding, navigation or water-related gameplay is required. Verify and, where necessary, repair the documented Unreal editor import integration for the project's engine version; do not silently substitute arbitrary water shapes or omit mandatory water geometry. If a required Water plugin API cannot represent the mandatory data, stop and report the blocker rather than claiming success. Any imported water-body count reduction, filtering threshold or simplified geometry must be explicitly authorized before implementation; use the complete exported data by default. Package all necessary water actors, assets and enabled built-in plugin dependencies so the water is visible in the installed game without external files or editor scripting. Record the exact water import workflow and any engine API limitations in the game README.

5. **New Game navigation.** Make the existing main-menu New Game action selectable and functional. Activating it replaces the main-menu content with a region-selection screen inside the existing application window (not a new operating-system window). Preserve the application's established resolution, fullscreen, localization and lifecycle behavior. Provide a Back action on the selection screen that returns to the main menu. Once a plot has loaded, pressing M opens the same full-region 10 × 10 selection screen, showing all 100 plots and highlighting the currently loaded plot with a 3-pixel cyan outline RGB `(0, 1, 1)`; pressing Escape from a loaded plot also opens this selection screen. While opened from a loaded plot, the existing plot remains loaded until the player chooses a destination; pressing Back or Escape closes the selection screen and resumes viewing the current plot. When the selection screen was opened from the main menu, Back or Escape instead returns to the main menu. The screen must not create a second copy of the landscape or reset the camera when dismissed.

6. **Overview.** The selection screen must display a top-down, terrain-derived overview of the complete 100 × 100 km region. Derive this overview deterministically from the actual generated elevation data: sample the full 100 × 100 km regional elevation grid into a 1024 × 1024 grayscale image using bilinear interpolation, map the minimum elevation in that region to black and the maximum to white, and preserve north-up orientation; do not use a hand-painted map or substitute unrelated imagery. Render the overview as a centred square occupying 80% of the smaller available viewport dimension, with a 1-pixel white grid dividing it into 10 × 10 cells, in correct geographic order, with west at left and north at top. The screen background is solid dark grey RGB `(0.1, 0.1, 0.1)`; display the existing localized title centred above the square and a plain rectangular Back button centred below it. Use the project's existing UI font and default button/text styles; do not add decorative images, icons, tooltips or animations. For this technical test, all one hundred squares are individually clickable, regardless of future gameplay eligibility. Indicate the square under the pointer using a 3-pixel yellow outline RGB `(1, 1, 0)`. Each square maps exactly to its corresponding `tile_x{col}_y{row}` landscape. The overview must be available in the packaged build and must not depend on external files at runtime.

7. **Selection and loading.** A single left click on a square opens only the corresponding plot's level and displays its real terrain. From an already loaded plot, selecting a different square unloads the previous plot and loads the chosen plot; selecting the currently loaded square simply closes the selection screen and preserves the current camera. During a plot-to-plot load, keep the selection screen visible, and if the new plot fails to load, retain or restore the previous plot and show the specified localized failure message. During loading, ignore further selection input and keep the selection screen visible until the destination level is ready; after success, remove the selection UI. Do not load all one hundred full-resolution landscapes simultaneously. Prevent duplicate load requests while a level transition is in progress. A load failure must not present an unrelated or empty landscape as a successful result; it must return to the selection screen with a clearly visible failure message. For this pipeline test only, the user must be able to select and enter any of the one hundred plots in a packaged build. This does not establish that every plot is playable in the finished game.

8. **Free camera.** After a successful load, place a free-flying, non-colliding spectator camera above the centre of the selected plot, facing due north with a 45-degree downward pitch so that terrain is visible. Use W/A/S/D for horizontal movement relative to camera heading, Q/E for down/up, hold the right mouse button and move the mouse to rotate, and each mouse-wheel notch to multiply/divide movement speed by `1.25` (wheel up/down), clamped to the defined range. Default movement speed is 100 m/s, bounded to 10–1000 m/s; default camera height is 500 m above the terrain at the plot centre. Mouse movement rotates yaw and pitch at `0.15°` per pixel, with pitch clamped between `-89°` and `89°`; the camera is not constrained by terrain collision. Camera movement is frame-time based and works while the game is not simulating time. Pressing M or Escape opens the region-selection screen while in a plot. The camera must not be attached to a player character and must not introduce a player pawn with gameplay capabilities.

9. **Time and gameplay scope.** This specification tests only map creation, terrain/water import, packaging, rendering, overview navigation and plot switching. It does not create a global simulation manager, simulation state, off-screen simulation, persistent gameplay entities, resource distribution, economic-benefit evaluation, playable-plot eligibility rules, or save-state infrastructure. Do not invent an eligibility filter, disabled-cell state, or resource data in this test. Loading or unloading a plot is a rendering/content operation, not a start/stop signal for any future world simulation. No in-game time progression, simulation ticks for economy/population/AI, building placement, resource processing, saving/loading a game, RPG mechanics or world interaction are introduced. Engine rendering and input continue normally. Existing application systems remain functional and unchanged except where explicitly required here.

10. **User-facing text.** Reuse the existing localized `MainMenu.NewGame` entry for the existing button. Add the following entries to the canonical Lord Simulator localization resources, preserving the existing supported cultures (`en`, `cs`, `uk`):
   - `NewGame.RegionSelection.Title`: en `Select a region`; cs `Vyberte oblast`; uk `Виберіть регіон`.
   - `NewGame.RegionSelection.Back`: en `Back`; cs `Zpět`; uk `Назад`.
   - `NewGame.RegionSelection.LoadFailed`: en `Unable to load the selected region.`; cs `Vybranou oblast se nepodařilo načíst.`; uk `Не вдалося завантажити вибраний регіон.`.
   The tile identifiers are technical identifiers, not translated names. Do not add other player-facing strings or tooltips.

11. **Verification.** Add deterministic Unreal automation coverage for the one hundred overview-cell-to-level mappings, source-data tile orientation, M-key opening, dismissal without reloading, plot-to-plot switching, reselecting the current plot, and missing/unavailable landscape handling. Validate water export and water import counts and positions against the generated per-plot data, and verify that water does not change terrain heights. Do not use an arbitrary visual resemblance as the sole evidence of correct data import. Verify in Unreal Editor and in a packaged Win64 Shipping build that New Game opens the overview, Back returns to the main menu, representative western/mountain and eastern/plain plots load with visibly different actual relief, the camera responds to the specified controls, generated rivers and lakes are correctly positioned and visible on representative plots, and all one hundred levels (including water) are included in cooked content. Perform or document an objective comparison of representative terrain heights against the generated heightmap data within one 16-bit height step (~0.078 m) and check plot orientation. Record any practical engine limitation encountered during the 4033-vertex landscape import or cooking rather than silently substituting a smaller or fake map. If the required one hundred landscapes or complete water geometry cannot be imported, cooked or loaded reliably on the supported target, stop and report the limitation; do not mark the spec accepted.

12. **Project-standard documentation.** Document the established map-selection, shared geographic plot identity, separately loaded rendering-level and offline-import architecture in `standards/PROJECT_STANDARD.md` in the documentation repository as part of this feature's completion. The update must describe only verified implemented behavior, must not change unrelated project-wide rules, and must remain consistent with this specification and the game project's README. Do not consider the specification complete until this documentation update is present.

# Acceptance Criteria

1. The existing New Game button opens the selection screen; while a plot is loaded, M or Escape opens the same 10 × 10 overview, and choosing a different plot loads it. Back or Escape dismisses an in-game overview without resetting the current plot, while Back or Escape from the initial overview returns to the main menu. Existing startup, settings and localization behavior remains unchanged.
2. The selection screen displays the specified 1024 × 1024 real-data-derived overview of the 100 × 100 km region with one hundred correctly ordered and individually selectable 10 × 10 km cells for testing purposes, using the specified simple boxes, grid, title and Back button.
3. Selecting each cell loads the matching separately cooked Unreal Landscape level; the running packaged game does not require external generation scripts or data files.
4. Loaded terrain preserves the documented resolution, horizontal dimensions, elevation scale and orientation; representative height checks pass within the stated quantization tolerance.
5. Only the selected high-resolution landscape is loaded, with the specified neutral material and basic lighting, complete generated rivers and lakes, and no foliage, structures or gameplay content.
6. The free camera starts above visible terrain and responds to W/A/S/D, Q/E, right-mouse rotation and mouse-wheel speed adjustment.
7. No game-time progression, economic simulation, RPG systems, global simulation framework or game-saving functionality is introduced. All 100 plots are treated as parts of one geographic world, but this technical test does not declare all plots playable in the eventual game or implement economic eligibility. Plot-level loading is not authoritative for future simulation state.
8. Duplicate load requests are prevented; switching plots unloads the previous plot, reselecting the current plot does not reload it, and failed switches preserve or restore the previous plot and show the defined localized error.
9. All required localized entries are available in English, Czech and Ukrainian, using the established localization framework.
10. The canonical seed-7 generation and all applicable validators pass; the documented water validation passes; generated river and lake actors appear in their correct terrain locations and water elevations in the Editor and packaged build, without terrain deformation or runtime external files. The defined automated checks pass, and the documented Editor and packaged Win64 Shipping verification steps are completed. The game-project README contains a reproducible generation/import/cook/build workflow.
11. `standards/PROJECT_STANDARD.md` documents the verified resulting region-selection and plot-loading architecture and is consistent with this specification and the implementation.
